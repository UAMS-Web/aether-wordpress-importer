# Continuous integration

The gate's jobs, what each one checks, and how the remote and local runs relate. [`AGENTS.md`](../AGENTS.md#running-things) carries the commands; this page carries the detail behind them. The runner's own flags are the [`local-ci`](../.claude/skills/local-ci/SKILL.md) skill's.

## The required remote checks

`main` requires three checks: `CI`, `Attribution footer` and `Closing keywords` (#163), the same three the Statamic add-ons require. `.github/workflows/ci.yml` calls the shared job chain in `UAMS-Web/uams-ci-workflows` from its `checks` job, pinned to a release tag (#415), and keeps `spell`, `node-test` and `python-test` as jobs of its own. The chain runs Composer validate, synced files, no-emoji, aggregate-needs, Pint, Rector, PHPStan, mutate-ignore, mutate and Pest, from this repository's checkout: its composite action `.github/actions/setup/action.yml`, the Composer scripts `test:pint`, `test:refactor`, `stan`, `test` and `mutate`, and `tests/skip-baseline.json`, the most skipped tests a run may report. Its checks report as `checks / <job name> (<operating system>)`, and it ends in `Chain result`, which fails unless each of them succeeded. Mutation testing runs in the chain (#519): its `mutate` job, on `ubuntu-latest` alone, mutates the PHP files under `src` that a pull request or a push changes, under a 45-minute limit, and everything `composer mutate` covers on the weekly `schedule` and on a manual `workflow_dispatch` run, under the chain's 180-minute full-run limit. It fails on any survivor. `CI` is the last job in `ci.yml`; it needs the call and the other jobs and fails unless each one succeeded, so a skipped or cancelled job fails it. Add a new job to its `needs:` list in the same change; `scripts/ci-local.test.mjs` fails otherwise. **Every job runs on `ubuntu-latest` and `windows-latest`** (#186), and its check name carries the operating system. The chain runs Composer validate, Pint, Rector and PHPStan on Linux alone unless they are named in `all-platform-jobs`, which this repository does; the chain has no Linux-and-Windows setting, so those four, Pest and mutate-ignore also run on `macos-latest`. `CI` itself runs once, on Linux; a matrix job's result covers every leg, so a failure on any fails `CI`. The same test fails when a job of `ci.yml` loses its Windows leg or gains `continue-on-error`, or when the call stops naming those four jobs. The other two are the jobs of `check-attribution-footer.yml` and `check-closing-keyword-across-lines.yml`. Every job but `CI` carries `if: vars.RUN_REMOTE_CI != 'false'`. The organization's variable is scoped to private repositories and does not reach this one, so only a repository variable switches those jobs off, and `CI` then fails rather than passing.

## The local runner

The runner is the shared one, [`.claude/skills/local-ci/local-ci.mjs`](../.claude/skills/local-ci/local-ci.mjs), configured by [`local-ci.json`](../local-ci.json) (wordpress-importer-archive#1319). [`scripts/ci-local.mjs`](../scripts/ci-local.mjs) only places its `--branch` slot, at `../wordpress-importer-local-ci`: the old `../wordpress-importer-ci` tree was made by the private runner this replaced, carries no runner marker, and the shared runner refuses to move it. Unlike `composer ci`, the runner does not abort at the first failure: one run surfaces everything the gate would flag. Read the summary block, not the exit code, and see the [`local-ci`](../.claude/skills/local-ci/SKILL.md) skill for `--comment`, `--commit-status` and the single-flight lock.

**The `dependencies` job is what keeps a reused slot honest.** In the runner's own slot it runs `composer install`, and runs `npm ci` when `node_modules/` differs from `package-lock.json`. Anywhere else it installs nothing and fails on drift, naming the command to run. See [`scripts/prepare-dependencies.mjs`](../scripts/prepare-dependencies.mjs).

## Changed tests against base

The additional `changed-tests` reporting job runs the shared `pest-testing` script locally and on Linux and Windows in Actions. It is listed in the aggregate `CI` job's `needs:`. It and `mutate-ignore-breadth` are mirrored in `local-ci.json` beside the eight jobs listed below. With no changed standalone test files, it reports nothing to compare without installing scratch dependencies.

Only `tests/Unit` and `tests/Integration` are selected, matching the standalone suites that package CI runs. **`tests/Feature` is deliberately excluded:** those tests require the consuming host application's `Tests\TestCase`, content model, and configuration, none of which this package boots. A successful report makes no claim about host-bound tests; changes to their behavior still require the separate host-app run described in [`tests/CLAUDE.md`](../tests/CLAUDE.md).

For each changed standalone `*Test.php` file, the script runs the pull request's tests against the merge base's source in an isolated scratch worktree with its own locked dependencies. It reads the base from `GITHUB_BASE_REF` in Actions and defaults to `origin/main` locally. The report appears in the log and the Actions job summary. A test failing against base is information, not a failed job: a bug fix can legitimately change behavior. An unavailable comparison, such as missing history or a test file that cannot run, fails the job rather than reporting a false pass.

The selected directories also define the PR-side support overlay. Changes inside `tests/Unit` and `tests/Integration` accompany the selected tests, but shared helpers outside them, including `tests/Pest.php`, `tests/StatamicTestCase.php`, and `tests/Support`, stay at base. When a changed test depends on a changed shared helper, read the report with that limitation in mind. Local comparisons read committed `HEAD`, not staged or unstaged test edits.

## The jobs

**The gate is eight jobs that mirror the remote checks: `validate`, `pint`, `phpstan`, `rector`, `pest`, `spell`, `node-test`, `python-test`**, plus three local-only ones: `dependencies`, `synced-files` (a hand edit to a file the shared sync manages) and `handed-back-workflow` (`.github/workflows/clear-handed-back.yml` against its shared template). Four of the eight are PHP, and `validate` runs `composer validate`: it catches a `composer.json` edit that left `composer.lock`'s content hash stale, which resolves fine and warns on every `composer install` until fixed. `pint` lints the whole tree plus every dot-directory holding tracked PHP, which Pint's Finder otherwise skips ([`scripts/run-pint.mjs`](../scripts/run-pint.mjs)). `spell` (wordpress-importer-archive#922, widened by wordpress-importer-archive#980) runs `cspell` over the prose corpus: `.claude/**/*.md`, `docs/**/*.md`, `README.md`, `AGENTS.md`, `CLAUDE.md`, `tests/CLAUDE.md` and `.github/**/*.md`, and refuses a run that checked zero files ([`scripts/run-spell.mjs`](../scripts/run-spell.mjs)). **`AGENTS.md` and the two `CLAUDE.md` files are in the corpus because they load into every session**, so they are the most-read prose here and were the least checked; `src/` stays out, per wordpress-importer-archive#922's reasoning that it spends the dictionary budget on WordPress field names for no prose coverage. `node-test` (wordpress-importer-archive#941) runs each `scripts/*.test.mjs` under Node's own runner, which needs no `node_modules` because those tests import only `node:` builtins and the shared runner. `python-test` (wordpress-importer-archive#1155) runs every `*.test.py` under `scripts/` and `.claude/skills/` through [`scripts/python-tests.mjs`](../scripts/python-tests.mjs), and fails, rather than skipping, when there is no Python 3 or nothing to run.

**Say what actually covered the diff, not that the gate was green.** The coverage is uneven and the shape matters: `spell` checks *spelling* in those paths and nothing else: not prose correctness, and not a Markdown file outside them. `node-test` exercises the scripts through their own tests. A `--branch` run hands off to the **branch's** copy of the shared runner when it differs from the invoking one, and prints `Handoff:` when it does, so a pull request that changes the runner is gated by the copy it ships. A change to `local-ci.json` alone needs no handoff, because the runner reads the job list from the branch's tree.

## The two mirrors

`.github/workflows/ci.yml` and `local-ci.json` are hand-maintained mirrors. `spell`, `node-test` and `python-test` mirror the jobs of `ci.yml` itself. `validate`, `pint`, `phpstan`, `rector` and `pest` mirror the called chain, whose jobs run the Composer scripts, so each of those local commands is its script with `vendor/bin/` in front (or the `node` command `test:pint` names). The chain runs `pest` whole on each runner, as `local-ci.json` does. `.githooks/pre-commit` blocks a commit that stages exactly one of `ci.yml` and `local-ci.json`; for a genuinely one-sided edit, `git commit --no-verify`. [`scripts/ci-local.test.mjs`](../scripts/ci-local.test.mjs) checks the parts that can be compared mechanically: every job of `ci.yml` and every chain job mirrored is in `local-ci.json`, each mirrored command matches, and the call pins a release tag.
